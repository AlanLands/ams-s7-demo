# Git workflow — {{team}}

Rules for working against `{{repository}}`. The Control Centre reads progress from this repository, so the conventions below are load-bearing, not style.

## The four phrases — what the developer says, what the agent does

The developer owns every commit and every push, and sees every acceptance criterion working before the next one starts. A coding agent acts on exactly these phrases and on nothing else:

| Developer says | Agent does | Never |
|---|---|---|
| `{{phrase_start}}` | Reads the story, writes the **build plan** — one section per acceptance criterion — into the story note, lays the red baseline, raises its open questions, stops | write implementation code, commit, stage, push |
| `{{phrase_build}}` | Builds **one acceptance criterion**, in the **working tree only**, until its test and the full suite are green, then hands the developer a way to see it working and stops | start a second criterion, commit, push |
| `{{phrase_commit}}` | Commits what the developer has just reviewed locally — red baseline first, implementation second | push, amend, squash, force |
| `{{phrase_push}}` | Runs the push checklist below in order and pushes the story branch | push on a red suite, push anything else |

Any other instruction is ordinary work in the working tree. The agent never writes implementation code without the build phrase, never commits on its own initiative, never stashes or resets the developer's uncommitted work, and never pushes without the push phrase.

## `{{phrase_start}}` — plan by criterion, do not code

1. The context branch `{{context_branch}}` is **read-only** — read `AGENTS.md` and `.s7/**` from it, never commit to it.
2. Fetch, then create the working branch from `origin/{{default_branch}}`, **not** from `{{context_branch}}` — branching off the context branch would drag `.s7/**` files into your pull request. One branch per story:
{{branch_rows}}
3. Read `.s7/stories/<story>/story.md` and `acceptance-criteria.md`; summarise the story, its criteria and its dependencies back to the developer before writing anything. If a dependency story is not merged on `origin/{{default_branch}}`, say so and stop.
4. Write the **build plan** into the story note — the first thing the story creates, before any implementation exists. **One section per acceptance criterion**, in the order they will be built, each carrying four things:
   - the criterion verbatim, with its id;
   - the S7 skeleton test that proves it, by name;
   - the **code plan** — the functions, modules and templates the criterion needs created or changed, each with one sentence on **why this criterion needs it**;
   - **how the developer will see it working** — the page, command or query a human can run to observe the criterion for themselves.

   The story note is one file per story:
{{note_rows}}
5. Copy the story's S7 test skeleton in **unchanged** (test names are how CI evidence joins to acceptance criteria). That red baseline is the only code written before the developer approves a criterion — no implementation, no stubs, no scaffolding, no "obvious" helpers.
6. **Raise the open questions.** List, numbered, everything the story does not settle that the code plan depends on — a choice between two existing services, an unstated default, a validation rule the criteria imply but never state, a boundary the architecture leaves open. Ask them now and **do not guess**: a wrong assumption discovered at review costs more than a question asked here. A question the developer cannot answer is escalated to the story author, never resolved by inventing an answer.
7. Report the plan and the questions, and **stop**. Nothing is implemented until the developer answers the blocking questions and gives the build phrase.

## `{{phrase_build}}` — one criterion, then show it working

8. One build phrase buys **exactly one acceptance criterion** — the next unticked section of the plan. Never two criteria on one phrase, never a criterion the plan does not name, never work ahead into the next section.
9. Build that criterion's whole slice in the **working tree only**: un-skip its skeleton test, implement the functions the code plan named, and keep going until that test **and the full suite** are green. Work inside one criterion is continuous — the developer is not asked to approve each function, because the criterion is the unit they can actually judge.
10. If the slice needs something the code plan did not name, add it to that criterion's section and say so in the report. If the criterion cannot be met as planned, stop and re-plan with the developer rather than improvising around it.
11. **Hand the criterion to the developer to check.** Report the files changed and the test summary, then give the most direct way a human can observe this criterion themselves: the page and the input to type, the command and the output to expect, the query and the rows it should return. Where the only honest observation is the automated test, say exactly that and give the command to run it — never describe a manual check that does not exist.
12. **Wait for what they saw.** The developer runs it and reports the observation in their own words; the agent compares that with the criterion. If what they describe does not match the criterion, the criterion is **not met** — fix it and hand it back. Record in that section what was run, what the developer observed, and when.
13. Tick the section, propose the next criterion, and **stop** again. Repeat until every criterion is ticked, then report the full list of changed files, the test summary and any open question. **Stop there.** The developer reviews the diff locally; nothing is committed until they say so.

## `{{phrase_commit}}` — commit what was reviewed

14. Two commits, in this order, so the history itself is the test-first evidence: first the tests alone (`US-1: red baseline for US-1-AC1..AC3 (TASK-001)`), then the implementation (`US-1: add sign-in form (TASK-001)`).
15. Every commit message starts with the story id and names the task id. The Control Centre matches progress by exactly this convention.
16. The implementation commit is made only with the full suite green; a red suite is reported, not committed. Never amend, never squash the baseline away, never commit secrets, `.env` or generated artifacts.
17. Never modify `AGENTS.md` or anything under `.s7/` — S7-managed; they change only via a Control Centre republish.

## Story-owned files — the rule that prevents merge conflicts

Parallel stories conflict when each one appends its own section to the same shared file. So a story branch **never edits** the shared, integration-owned files:
- `README.md`
- `architecture.md`
- the shared application config (`application.yml`, `settings.py`, `.env.example`)
- CI workflows
- `AGENTS.md` and `.s7/**`

A story branch writes only to files it owns:

18. Its own packages, modules, templates and tests.
19. Its **story note** — one file per story, created at rule 4 and carrying the per-criterion build plan and its verifications, then every config key with its default, the feature flag, endpoints, and follow-ups. After the merge, the team lead folds the note into `README.md` and `architecture.md` in a docs-only commit on its own branch.
20. Its feature flag's default (**off**) declared in code — the properties class or settings constant — so the shared config needs no edit. Where the stack composes config from a directory, the story's keys go in its own fragment (`config/<story-id>.yml`); otherwise they are documented in the story note only.
21. The dependency manifest (`pom.xml`, `package.json`, `requirements.txt`) is the one shared file a story may touch: one minimal hunk, in its own commit, named for the story. An identical addition on two branches merges clean; a differing one is resolved on the story branch at the freshness check — never on `{{default_branch}}`.

## `{{phrase_push}}` — the push checklist

When the developer says this, run the checklist **in order** and refuse to push if any step fails:

22. **Scope check** — only files inside Allowed Components and the story-owned files above changed; nothing staged under `.s7/` or `AGENTS.md`; no shared file edited.
23. **Plan check** — every criterion's section in the story note is ticked and carries the developer's own recorded observation, and nothing was built that no section named. A criterion nobody looked at is not done.
24. **Acceptance check** — every criterion in `.s7/stories/<story>/acceptance-criteria.md` has a passing test; run the full suite. **Red suite = no push** — report the failures instead.
25. **Traceability check** — every commit on the branch references the story id; working tree clean.
26. **Freshness check** — fetch and rebase on latest `origin/{{default_branch}}`, re-run the full suite after the rebase. Conflicts are resolved here, on the story branch, by the story author.
27. **UI evidence** — for any story that adds or changes a page, the screenshots `.s7/shared/ui-guidelines.md` asks for are ready for the pull request body. For a UI criterion, the screenshot the developer took at rule 11 *is* that evidence.
28. **Push the story branch only** — `git push -u origin feature/<story-id>-…`. Never push to `{{default_branch}}`, never push to `s7/**`, never `--force` a shared branch. After a rebase, `--force-with-lease` on your **own** story branch is the only force ever permitted.
29. **Report back** — branch, commit list, test summary; the developer opens the pull request, and the Control Centre's *Sync from Git* shows the progress.

## Pull request & merge rules

30. PR title starts with the story id; the body maps each acceptance criterion to its test evidence **and to the developer's recorded observation of it**, carries the UI screenshots, and links the story note; target is `{{default_branch}}`.
31. The author never merges their own PR — no self-approval.
32. **One merge at a time.** After any PR merges, every other open story branch re-runs the freshness check (fetch, rebase, full suite, `--force-with-lease` on its own branch) **before** the next merge. Nobody resolves a conflict on `{{default_branch}}` by hand.
33. Merging is always a human action. After the merge, *Sync from Git* marks the workspace complete — that is the only way a story completes.

## Prohibited, always

34. Writing implementation code without the build phrase; building more than the one criterion approved; generating a whole story in one pass; ticking a criterion the developer never observed; guessing an answer to an open question instead of asking it; pushing to `{{default_branch}}` directly; pushing to any `s7/**` branch; force-pushing shared branches; deleting branches you do not own; committing without the commit phrase; committing credentials; editing a shared file on a story branch; declaring done with failing tests.
