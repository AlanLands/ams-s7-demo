# Git workflow — {{team}}

Rules for working against `{{repository}}`. The Control Centre reads progress from this repository, so the conventions below are load-bearing, not style.

## The three phrases — what the developer says, what the agent does

The developer owns every commit and every push. A coding agent acts on exactly these phrases and on nothing else:

| Developer says | Agent does | Never |
|---|---|---|
| `{{phrase_start}}` | Prepares the branch, builds the change in the **working tree only**, runs the suite, reports | commit, stage, push |
| `{{phrase_commit}}` | Commits what the developer has just reviewed locally — red baseline first, implementation second | push, amend, squash, force |
| `{{phrase_push}}` | Runs the push checklist below in order and pushes the story branch | push on a red suite, push anything else |

Any other instruction is ordinary work in the working tree. The agent never commits on its own initiative, never stashes or resets the developer's uncommitted work, and never pushes without the push phrase.

## `{{phrase_start}}` — build, do not commit

1. The context branch `{{context_branch}}` is **read-only** — read `AGENTS.md` and `.s7/**` from it, never commit to it.
2. Fetch, then create the working branch from `origin/{{default_branch}}`, **not** from `{{context_branch}}` — branching off the context branch would drag `.s7/**` files into your pull request. One branch per story:
{{branch_rows}}
3. Read `.s7/stories/<story>/story.md` and `acceptance-criteria.md`; summarise the story, its criteria and its dependencies back to the developer before writing code. If a dependency story is not merged on `origin/{{default_branch}}`, say so and stop.
4. Copy the story's S7 test skeleton in **unchanged** (test names are how CI evidence joins to acceptance criteria), then implement within Allowed Components until the full suite is green.
5. Report: the list of changed files, the test summary (before and after), anything that touched a shared file, and any open question. **Stop there.** The developer reviews the diff locally; nothing is committed until they say so.

## `{{phrase_commit}}` — commit what was reviewed

6. Two commits, in this order, so the history itself is the test-first evidence: first the tests alone (`US-1: red baseline for US-1-AC1..AC3 (TASK-001)`), then the implementation (`US-1: add sign-in form (TASK-001)`).
7. Every commit message starts with the story id and names the task id. The Control Centre matches progress by exactly this convention.
8. The implementation commit is made only with the full suite green; a red suite is reported, not committed. Never amend, never squash the baseline away, never commit secrets, `.env` or generated artifacts.
9. Never modify `AGENTS.md` or anything under `.s7/` — S7-managed; they change only via a Control Centre republish.

## Story-owned files — the rule that prevents merge conflicts

Parallel stories conflict when each one appends its own section to the same shared file. So a story branch **never edits** the shared, integration-owned files:
- `README.md`
- `architecture.md`
- the shared application config (`application.yml`, `settings.py`, `.env.example`)
- CI workflows
- `AGENTS.md` and `.s7/**`

A story branch writes only to files it owns:

10. Its own packages, modules, templates and tests.
11. Its **story note** — one file per story, created by the story, holding what was built, every config key with its default, the feature flag, endpoints, and follow-ups:
{{note_rows}}
    After the merge, the team lead folds the note into `README.md` and `architecture.md` in a docs-only commit on its own branch.
12. Its feature flag's default (**off**) declared in code — the properties class or settings constant — so the shared config needs no edit. Where the stack composes config from a directory, the story's keys go in its own fragment (`config/<story-id>.yml`); otherwise they are documented in the story note only.
13. The dependency manifest (`pom.xml`, `package.json`, `requirements.txt`) is the one shared file a story may touch: one minimal hunk, in its own commit, named for the story. An identical addition on two branches merges clean; a differing one is resolved on the story branch at the freshness check — never on `{{default_branch}}`.

## `{{phrase_push}}` — the push checklist

When the developer says this, run the checklist **in order** and refuse to push if any step fails:

14. **Scope check** — only files inside Allowed Components and the story-owned files above changed; nothing staged under `.s7/` or `AGENTS.md`; no shared file edited.
15. **Acceptance check** — every criterion in `.s7/stories/<story>/acceptance-criteria.md` has a passing test; run the full suite. **Red suite = no push** — report the failures instead.
16. **Traceability check** — every commit on the branch references the story id; working tree clean.
17. **Freshness check** — fetch and rebase on latest `origin/{{default_branch}}`, re-run the full suite after the rebase. Conflicts are resolved here, on the story branch, by the story author.
18. **UI evidence** — for any story that adds or changes a page, the screenshots `.s7/shared/ui-guidelines.md` asks for are ready for the pull request body.
19. **Push the story branch only** — `git push -u origin feature/<story-id>-…`. Never push to `{{default_branch}}`, never push to `s7/**`, never `--force` a shared branch. After a rebase, `--force-with-lease` on your **own** story branch is the only force ever permitted.
20. **Report back** — branch, commit list, test summary; the developer opens the pull request, and the Control Centre's *Sync from Git* shows the progress.

## Pull request & merge rules

21. PR title starts with the story id; the body maps each acceptance criterion to its test evidence and carries the UI screenshots; target is `{{default_branch}}`.
22. The author never merges their own PR — no self-approval.
23. **One merge at a time.** After any PR merges, every other open story branch re-runs the freshness check (fetch, rebase, full suite, `--force-with-lease` on its own branch) **before** the next merge. Nobody resolves a conflict on `{{default_branch}}` by hand.
24. Merging is always a human action. After the merge, *Sync from Git* marks the workspace complete — that is the only way a story completes.

## Prohibited, always

25. Pushing to `{{default_branch}}` directly; pushing to any `s7/**` branch; force-pushing shared branches; deleting branches you do not own; committing without the commit phrase; committing credentials; editing a shared file on a story branch; declaring done with failing tests.
