# Git workflow — {{team}}

Rules for working against `{{repository}}`. The Control Centre reads progress from this repository, so the conventions below are load-bearing, not style.

## The four phrases — what the developer says, what the agent does

The developer owns every commit and every push, and approves every function before it is written. A coding agent acts on exactly these phrases and on nothing else:

| Developer says | Agent does | Never |
|---|---|---|
| `{{phrase_start}}` | Reads the story, writes the **build plan** into the story note, lays the red baseline, proposes the first function, stops | write implementation code, commit, stage, push |
| `{{phrase_build}}` | Implements **exactly the one function just proposed** — test first — runs the suite, reports, proposes the next, stops | implement a second function, work ahead, commit, push |
| `{{phrase_commit}}` | Commits what the developer has just reviewed locally — red baseline first, implementation second | push, amend, squash, force |
| `{{phrase_push}}` | Runs the push checklist below in order and pushes the story branch | push on a red suite, push anything else |

Any other instruction is ordinary work in the working tree. The agent never writes implementation code without the build phrase, never commits on its own initiative, never stashes or resets the developer's uncommitted work, and never pushes without the push phrase.

## `{{phrase_start}}` — plan, do not code

1. The context branch `{{context_branch}}` is **read-only** — read `AGENTS.md` and `.s7/**` from it, never commit to it.
2. Fetch, then create the working branch from `origin/{{default_branch}}`, **not** from `{{context_branch}}` — branching off the context branch would drag `.s7/**` files into your pull request. One branch per story:
{{branch_rows}}
3. Read `.s7/stories/<story>/story.md` and `acceptance-criteria.md`; summarise the story, its criteria and its dependencies back to the developer before writing anything. If a dependency story is not merged on `origin/{{default_branch}}`, say so and stop.
4. Write the **build plan** into the story note — the first thing the story creates, before any implementation exists. One row per function the story needs, each naming the function, the acceptance criterion it serves, one sentence on **why it is needed**, the files it will touch and the test that will prove it:
{{note_rows}}
5. Copy the story's S7 test skeleton in **unchanged** (test names are how CI evidence joins to acceptance criteria). That red baseline is the only code written before the developer approves a function — no implementation, no stubs, no scaffolding, no "obvious" helpers.
6. Propose the **first function only**, in one short block — name, criterion, why it is needed, files, test — and **stop**. Nothing is implemented until the developer gives the build phrase.

## `{{phrase_build}}` — one function, then stop

7. One build phrase authorises **exactly the function just described** and nothing else. Never two functions on one approval, never work ahead of the approved row, never a stub or placeholder for a later row.
8. Write or un-skip that function's test first, implement the smallest function that makes it pass, then run the **full** suite — not only the new test.
9. Report in a few lines: the files changed, the test summary before and after, and the criterion now covered. Tick that row in the story note.
10. Propose the **next** function in the same short form and **stop** again. Repeat until the plan is done. Work the plan did not name is proposed as a new row of its own and never folded silently into the function in hand; if the plan itself turns out to be wrong, say so and re-plan with the developer rather than improvising.
11. When the last row is done, report the full list of changed files, the test summary and any open question. **Stop there.** The developer reviews the diff locally; nothing is committed until they say so.

## `{{phrase_commit}}` — commit what was reviewed

12. Two commits, in this order, so the history itself is the test-first evidence: first the tests alone (`US-1: red baseline for US-1-AC1..AC3 (TASK-001)`), then the implementation (`US-1: add sign-in form (TASK-001)`).
13. Every commit message starts with the story id and names the task id. The Control Centre matches progress by exactly this convention.
14. The implementation commit is made only with the full suite green; a red suite is reported, not committed. Never amend, never squash the baseline away, never commit secrets, `.env` or generated artifacts.
15. Never modify `AGENTS.md` or anything under `.s7/` — S7-managed; they change only via a Control Centre republish.

## Story-owned files — the rule that prevents merge conflicts

Parallel stories conflict when each one appends its own section to the same shared file. So a story branch **never edits** the shared, integration-owned files:
- `README.md`
- `architecture.md`
- the shared application config (`application.yml`, `settings.py`, `.env.example`)
- CI workflows
- `AGENTS.md` and `.s7/**`

A story branch writes only to files it owns:

16. Its own packages, modules, templates and tests.
17. Its **story note** — one file per story, created at rule 4 and carrying the build plan, then what was built, every config key with its default, the feature flag, endpoints, and follow-ups. After the merge, the team lead folds the note into `README.md` and `architecture.md` in a docs-only commit on its own branch.
18. Its feature flag's default (**off**) declared in code — the properties class or settings constant — so the shared config needs no edit. Where the stack composes config from a directory, the story's keys go in its own fragment (`config/<story-id>.yml`); otherwise they are documented in the story note only.
19. The dependency manifest (`pom.xml`, `package.json`, `requirements.txt`) is the one shared file a story may touch: one minimal hunk, in its own commit, named for the story. An identical addition on two branches merges clean; a differing one is resolved on the story branch at the freshness check — never on `{{default_branch}}`.

## `{{phrase_push}}` — the push checklist

When the developer says this, run the checklist **in order** and refuse to push if any step fails:

20. **Scope check** — only files inside Allowed Components and the story-owned files above changed; nothing staged under `.s7/` or `AGENTS.md`; no shared file edited.
21. **Plan check** — every row of the build plan in the story note is ticked, and nothing was built that the plan never named.
22. **Acceptance check** — every criterion in `.s7/stories/<story>/acceptance-criteria.md` has a passing test; run the full suite. **Red suite = no push** — report the failures instead.
23. **Traceability check** — every commit on the branch references the story id; working tree clean.
24. **Freshness check** — fetch and rebase on latest `origin/{{default_branch}}`, re-run the full suite after the rebase. Conflicts are resolved here, on the story branch, by the story author.
25. **UI evidence** — for any story that adds or changes a page, the screenshots `.s7/shared/ui-guidelines.md` asks for are ready for the pull request body.
26. **Push the story branch only** — `git push -u origin feature/<story-id>-…`. Never push to `{{default_branch}}`, never push to `s7/**`, never `--force` a shared branch. After a rebase, `--force-with-lease` on your **own** story branch is the only force ever permitted.
27. **Report back** — branch, commit list, test summary; the developer opens the pull request, and the Control Centre's *Sync from Git* shows the progress.

## Pull request & merge rules

28. PR title starts with the story id; the body maps each acceptance criterion to its test evidence, carries the UI screenshots, and links the story note so the reviewer can read the build plan that was agreed; target is `{{default_branch}}`.
29. The author never merges their own PR — no self-approval.
30. **One merge at a time.** After any PR merges, every other open story branch re-runs the freshness check (fetch, rebase, full suite, `--force-with-lease` on its own branch) **before** the next merge. Nobody resolves a conflict on `{{default_branch}}` by hand.
31. Merging is always a human action. After the merge, *Sync from Git* marks the workspace complete — that is the only way a story completes.

## Prohibited, always

32. Writing implementation code without the build phrase; implementing more than the one function approved; generating a whole file or a whole story in one pass; pushing to `{{default_branch}}` directly; pushing to any `s7/**` branch; force-pushing shared branches; deleting branches you do not own; committing without the commit phrase; committing credentials; editing a shared file on a story branch; declaring done with failing tests.
