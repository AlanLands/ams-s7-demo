# Database conventions

**Use when:** a criterion adds, changes or reads persistent data — schema, migration, config or seed data.

Rules for every story that adds, changes or reads persistent data. They exist for the same reason as the git workflow: parallel stories that each edit the same schema file or the same config file are how merges conflict, and a migration that changes after it has run is how environments drift apart.

## Schema changes are story-owned

1. A story that changes the schema ships **one forward-only migration**, created by the story and named for it. A story never edits a shared `schema.sql`, a shared entity file it does not own, or another story's migration.
2. Naming — Flyway (Java): `V<next>__<story-id-lowercase>_<short-desc>.sql`, Flyway's `V<version>__<description>.sql` convention with the double underscore, for example `V7__us-003_add_claim_status.sql`. Take `<next>` at the freshness check, after rebasing on `origin/{{default_branch}}`, so two stories never claim the same version. Alembic (Python): one revision per story, `alembic revision -m "<story-id>: <short-desc>"`, with `down_revision` set at the freshness check for the same reason.
3. A migration is **never edited after merge**. A mistake is corrected by the next migration, on a new story branch, named for the story that corrects it.
4. A story **owns the tables it creates** and lists them — table, purpose, retention — in its story note, so the team lead can fold them into `architecture.md` after the merge:
{{note_rows}}
5. Every migration is reversible in intent: the story note records how the change is rolled back (a down migration, a feature flag that stops reading the new column, or "additive, no rollback needed"), and the rollback plan on the story references it.

## Configuration stays out of the shared file

6. A story's settings go in **its own fragment**, never in the shared application config. Spring: `src/main/resources/config/<story-id>.yml`, loaded by `spring.config.import: optional:classpath:config/` — Spring loads every file in the directory alphabetically, so no story edits `application.yml` to register its keys. Python: a `config/<story-id>.py` settings fragment imported by the settings module's fragment loader.
7. Every key in the fragment has a default declared in code (the properties class or settings constant) and is listed in the story note with that default. Connection strings, credentials and anything environment-specific come from the environment, never from a fragment.

## Persistence before the store exists

8. Where the story's data store is owned by a Data Team story that has not merged yet, an **in-memory store behind an interface** is acceptable until it lands. The interface is the seam: the consuming story codes and tests against it, the Data Team story provides the persistent implementation, and the switch is a wiring change, not a rewrite. The story note names the interface and the dependency.

## Data

9. Synthetic seed data lives **only in a dev profile** (`application-dev.yml`, a dev-only fixture module, a `data-dev.sql` guarded by the profile) and is never loaded by a migration.
10. **No PII** in fixtures, migrations, seed data or logs — synthetic names, organisations and plan numbers only; log record ids, never record contents.
11. The dependency-manifest rule from the git workflow applies to database drivers and migration tools: one minimal hunk, in its own commit, named for the story.
