# Debugging — {{team}}

**Use when:** a test fails, a build breaks, CI is red, or anything behaves other than you expected — **before** you propose or apply a fix. Including when the cause looks obvious.

A fix applied without finding the cause either does nothing or hides the problem until someone else finds it. Within a story that costs an afternoon; after a merge it costs the release.

## Before any fix

1. **Read the whole error.** The message, the stack trace, the line number, the exit code. Read it to the end rather than to the first familiar word — the answer is in it more often than not.
2. **Reproduce it.** Run the failing thing again on its own. Does it fail every time? What exactly triggers it? If it is intermittent, say so and gather more before touching anything — an intermittent failure fixed by guesswork is still there.
3. **Check what changed.** Your own diff first, then the branch, then what arrived from `origin`. Something worked at some point; find the last point it did.
4. **Follow the bad value back.** Where does the wrong value first appear? What put it there? Keep going up until you reach the thing that is actually wrong, and fix it there. A wrong value corrected at the point it was noticed leaves the source intact for the next caller.
5. **Find something that works.** A similar path in this repository that behaves correctly is the fastest way to see what is different about the broken one. List every difference before deciding which one matters.

## Making the fix

6. **Say the cause out loud first**, in one sentence: *"The page 404s because the controller is registered under `/login` and the template links to `/signin`."* If you cannot finish that sentence, you have not found the cause yet — go back.
7. **Change one thing.** One hypothesis, one edit, one run. Bundling three changes and seeing green tells you nothing about which one mattered, and leaves two unexplained edits in the diff.
8. **Verify it properly** — `verification.md`: re-run the original failure, then the full suite with `{{suite_command}}`. "The error stopped appearing" is not the same as "the cause is gone".
9. **Fix only the failure.** No tidying, no refactoring, no "while I'm here". Those are separate work and they hide the fix inside noise the developer then has to read past.

## When it does not work

10. **Count your attempts.** After the third failed fix, stop. Do not try a fourth.
11. **Take it to the developer** with what you know: what fails, what you have ruled out, what each attempt assumed and what actually happened. Three failures that each reveal a new problem somewhere else usually means the approach in the criterion's plan is wrong, not that the next fix is nearly right — and the plan is the developer's to change.
12. **Never quietly work around it.** Do not weaken the test (`verification.md` § Test integrity), do not skip it, do not stub the behaviour out, do not build something the plan does not name to route around the problem. Say you are stuck. Being stuck is a normal report; a green test over a broken feature is not.

## Do not say

"It should work now", "that probably fixed it", "the error is gone" — without having re-run the thing that failed. See `verification.md`.
