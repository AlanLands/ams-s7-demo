S7 · Solution Overview

Business requirement to evidence-backed release

S7 is the governed control plane for an AI-assisted SDLC. Humans own implementation; S7 generates governed context, publishes it, collects real delivery evidence and orchestrates independent review.
S7Full-Scale Application Development & Delivery
Human controlled
Named business, engineering and QA gates prevent any phase from self-approving. Merging is always a human act.
Grounded in the estate
Every AI call is grounded in the connected repositories and each application's own architecture context — a file in the repo, not a fine-tune.
Evidence backed
Acceptance criteria, tests, real CI results, reviewer findings and approvals are joined into the release record — measured, never claimed.

S7 · Solution Overview01 / 06
Agents inside S7

Separate roles, separate guardrails, one gateway

Each agent has a bounded responsibility and its own prompt. The operating model separates intake and planning, developer execution, and independent review — so no role grades its own work.
S7Agent operating model
A
Upstream · Control Centre
Requirement Extraction Agent
Turns .txt / .md / .pdf / .docx input into a structured requirement: title, objective, summary, numbered requirement bullets.
Requirement Routing Agent
Chooses an already-onboarded application or a new-application path. A human can override the verdict.
Intake Analysis Agent
Analyzes the epic against the connected repositories, extracts business rules, sizes the change, raises its own clarification questions.
Clarification Agent
Runs a capped Q&A with the business owner. Questions come from the analysis; the recorded answers feed the plan.
New-Application Setup Agent
Produces a reviewable architecture + README scaffold for human approval before any repository is created.
Delivery Planning Agent
Creates stories, tasks, acceptance criteria, team assignments, estimates and dependencies — with one bounded self-correction pass before a human sees the plan.
Architecture Refinement Agent
Refines a lead's proposed architecture change into a new immutable version. Human acceptance always resets.
Test-Plan Refinement Agent
Refines a QA lead's proposed amendment into additional cases as an overlay, then returns the pack to QA approval.
B
Downstream · Developer workspace & independent review
Developer Agent
Implements the task in the developer's own CLI workspace, grounded in AGENTS.md, acceptance criteria and approved architecture context. Reviewer findings triage back to it — never a blind retry.
Test Engineer Agent
Authors and runs the change's tests from the deliberately failing per-AC skeletons — so the evidence is a real red-to-green transition, per criterion.
Independent Reviewer Agent
Isolated from developer and tester roles. Reviews the finished change against the acceptance criteria — not the tests — issues the G2 verdict and returns named findings for revision.
Deliberately not agents
Deterministic services that cannot invent results
Architecture-pack assembly, delivery packs, rule-derived test skeletons, git publication, dependency wave gating, CI evidence joins, staleness tracking, quality checks and the release document are computed from real run data.

One audited gateway — every agent call runs through a single LLM module with per-call telemetry, pointed at any OpenAI-compatible endpoint: CL's enterprise gateway or a self-hosted model.
S7 · Solution Overview02 / 06
No phase self-approves

Human gates make the decisions; deterministic checks judge the evidence

The quality gate combines an isolated reviewer verdict with nine checks computed from the run's real evidence. A check that is arithmetic over evidence cannot hallucinate — which is why it sits in judgment over the agents.

S7 · Solution Overview03 / 06
Ten core capabilities

A governed engineering system — not ad-hoc prompting

The capability set is designed around ordered phases, immutable versions, traceability, and machine-checkable completeness before human review.
S7Core capabilities
1
Gated pipeline
A server-validated phase machine from intake to release. Out-of-order actions are refused; each gate requires its named artifacts and sign-off.
2
Four-layer architecture
Stable rules, role prompts, reference context and task delta assembled in fixed order, driven by one orchestrator.
3
Story quality standards
Purpose, testable ACs, dependencies, owning team and estimate enforced at planning time — one bounded self-correction pass repairs defective drafts.
4
Provenance ledger
Every artifact records what produced it, when, and which upstream artifact it derives from. Revisions create new immutable versions.
5
Factory activity log
Per-call telemetry including cache read/write tokens; an approvals ledger records every gate decision and who took it.
6
Independent review protocol
An isolated reviewer verifies acceptance criteria against the finished change. Critical or major gaps block and route back by role.
7
Traceability matrix
Acceptance criteria carry ids traced requirement → story → task → test → CI result; the release document renders each criterion with its evidence.
8
Self-correction & change management
Propose → refine → re-approve loops for architecture and test plans. Every change creates a new version and resets acceptance.
9
Completeness gates
Machine-checkable checks before human review: every business rule claimed by a story, every acceptance criterion testable and covered.
10
Staleness detection
When upstream artifacts change, downstream packs, workspaces and evidence are marked stale and must be regenerated before release.
Control plane
Governed orchestration, state, versions, evidence and approvals — one small VM, local files, no estate integration.
Developer-owned implementation
Build and test happen in the developer's own IDE / CLI / Git environment — Human Controlled · AI Assisted.
No invented evidence
Where run data does not exist, S7 reports nothing rather than a guess — the same discipline for KPIs, checks and documents.
Built to port — plain Python with pinned dependencies, local state, and deterministic replay of every rehearsed run: a fresh install with no API key still executes the full pipeline offline, which is how the system survives a locked-down environment.

End-to-end coverage, visible in artifacts, evidence and sign-offs

S7's claim is coverage of the SDLC's deliverables, not depth in any one of them: each phase produces a named, versioned artifact with visible provenance, and that artifact is the input to the next phase's gate.

IP
IP & data boundary
Ownership boundary
The control plane and tooling are our IP. Plans, architecture packs, delivery packs, test plans, evidence records and release documents it produces are CL's.
Model boundary
The LLM is accessed under enterprise terms with no training on CL data; the gateway / self-hosted option keeps CL code and data inside their boundary.
Estate boundary
The only content written into CL's estate is governed context on disposable branches that a CL human chooses to merge — or not.
Measurement discipline — every gate decision, agent session and LLM call is logged (including cache read/write tokens); each KPI traces to the records behind it. Where the data does not exist yet, S7 reports nothing rather than a guess.
