through **new-application workspace creation, GitHub repository creation, and
push verification**. This document records what was reset, what ran, what

## 2. Issues discovered, root causes, fixes

All three defects were found during the first live run and fixed **before**
the clean rerun, in commit `54c3690`
(`fix: intake clarification & new-app setup forms — dense answer arrays,
auto-continue, created-repo state`). Files changed:

- `apps/control/web/src/pages/intake/AdvancedAnalysisSection.tsx`
- `apps/control/web/src/types.ts` (added `transcript` to `NewAppState`)
- `apps/control/web/dist/**` (rebuilt in the same commit, per the hard-rule-4
  amendment: the server serves `dist/`, so src and dist must move together)

### Issue 1 — clarification submit 409s whenever any field is left blank

- **Symptom:** clicking *Submit answers* with any untouched
  “blank = stated assumption” field silently did nothing; server log showed
  `POST /intake/clarify-answer → 409 Conflict`.
- **Root cause:** the component kept answers in a sparse local array
  (`clarAnswers`), populated only for indexes the user typed into. The
  payload was therefore shorter than the pending-question list, and the
  engine correctly rejects a count mismatch
  (`EngineError: Expected N answers, got M` — `s7_delivery/factory/engine.py:624`).
  The advertised blank-answer path could never work from the UI. (A second
  form of the same bug: typing only into a *later* field produced `null`
  holes, which pydantic rejects with 422.)
- **Fix:** build the payload by mapping over the pending questions —
  `clar.pending.map((_, i) => clarAnswers[i] ?? '')` — so every question
  always gets an entry and blanks are sent as `''` (which the engine records
  as “(no answer — make a stated assumption)”). Local answer state now clears
  on success so answers cannot bleed into a later round at shifted indexes.
- **Validation (clean run):** answered Q1 only, left Q2–Q4 untouched, one
  click → `200 OK`; transcript shows all four Q/A pairs, three of them as
  stated assumptions. Round counter advanced 1→used, pending cleared.

### Issue 2 — new-application setup silently “resets” after answering

- **Symptom:** after submitting the setup answer, the panel fell back to the
  *Start New Application Setup* button; clicking it again (non-obviously)
  resumed and finalized. Looked like lost state.
- **Root cause:** by design, `POST /intake/new-app-answer` only *records*
  answers (`engine.intake_new_app_answer`); the next assistant turn
  (follow-up questions or finalization) only happens on the next
  `POST /intake/new-app-setup`. The UI never made that second call, so the
  panel rendered its fall-through state. Same sparse-array bug as Issue 1
  was latent in this form too.
- **Fix:** the submit handler now sends a dense answers array and, on
  success, **chains the `new-app-setup` call automatically** — one user
  action carries the conversation forward. The fallback button (still
  reachable if the chained call fails) is relabelled *Continue Setup*
  whenever a transcript exists.
- **Validation (clean run):** one click on *Submit answers* went
  answer → auto-setup → finalized `name/description/stack` with no manual
  re-click (server log shows the chained `new-app-setup` call; transcript
  has 2 entries; `pending` empty).

### Issue 3 — “Create Repository” button survives repo creation

- **Symptom:** after the repo was created for real, the panel still showed
  the *Create Repository* button; clicking it again 409'd server-side
  (correctly guarded) but the UI looked broken and invited double-submits.
- **Root cause:** the render condition only checked `scaffold` presence; the
  created repo is normalized into the ordinary connected-repos list
  (`intake/repos.json`), and the panel never consulted it.
- **Fix:** the panel now derives
  `newAppRepoCreated = repos.some(r => r.name === newApp.name)` and, once
  true, replaces the button with a confirmation line
  (“✓ Repository *name* created and connected — it now grounds analysis like
  any connected repository.”).
- **Validation (clean run):** after creation the button is gone and the
  confirmation renders; the repo appears in Connected Repositories with its
  head SHA and file count.

### Known limitation (observed, not fixed — deliberate)

The Intake page's state polling re-renders the page every few seconds. For a
human typing in one field this is harmless (controlled inputs keep their
values), but it can steal scroll position, and it made coordinate-based UI
automation flaky throughout testing. Not addressed in this pass because it
needs a considered fix (pausing polls while a form is dirty, or reconciling
without remount) rather than a patch. Tracked as a later item.

No architectural or flow changes were made — all three fixes are contained in
the intake frontend; the engine and API are unchanged (415 pytest tests green
before and after).
